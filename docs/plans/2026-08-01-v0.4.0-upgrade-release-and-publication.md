# Lawyer Assistance v0.4.0 升级、回滚与发布冻结计划

> 日期：2026-08-01
>
> 状态：已冻结，作为 Phase 7 之后 `v0.4.0` 发布阶段的唯一执行顺序
>
> 基线：`main` 合并提交 `955a08da82b5148449f5039e20643179c4df7a23`

## 1. 目的与边界

本计划补齐 `v0.3.1 → v0.4.0` 的真实升级、完整回滚、稳定版版本同步、签名资产、
服务端回读和正式发布门禁。它不重新设计 Phase 3–7 已完成的信息架构、出站模型、
Provider/MCP 协议或 ADR-0001 身份契约。

第 4–8 节的原态回滚 wire、receipt chain、lineage 和恢复边界的实现级冻结见
[`ADR-0002`](../adr/0002-v031-upgrade-rollback-protocol.md)。该 ADR 只按数据安全与最小
变更优先级澄清编码和恢复细节，不改变本计划的阶段顺序、提交分层或完成判定。

必须继续满足：

- `ProjectId` 是应用案件、项目和前端工作流身份；
- `PrivacyCaseId` 是 Privacy、Vault、脱敏、签名和 approved MCP 内部身份；
- 两者只通过持久化、不可变、一对一的审计绑定关联；
- 不修改既有 `projects.project_id` 或引用行，不通过字符串相等、替换、排序、相似度、
  哈希截断或计数器推导另一身份；
- 历史关联只能无歧义保留原 Privacy identity；歧义状态 fail closed；
- 普通 V3 application backup、当前 schema restore 和生产出站边界不得为旧版升级而放宽。

本计划的第一提交只允许修改计划文档。代码、版本号和发布状态从后续独立提交开始变化。

## 4. Exact migration-source validator

### 4.1 用户库

新增只用于升级源的只读 validator，返回 `V031V10` 或 `CurrentV11`。普通 current validator
仍只接受 v11。v10 validator 必须：

- 使用固定普通单链接路径、只读 SQLite flags、`query_only=ON` 和 deferred read transaction；
- 精确验证 schema version、canonical marker 和 74 个非内部 schema 对象；
- 覆盖完整 table DDL、PK、UNIQUE、CHECK、FK、index 和 trigger body；
- 执行 `quick_check`、`foreign_key_check` 及 v10 项目/会话/消息/附件/artifact/run/proposal
  关系验证；
- 在事务前后验证文件 identity、hash、schema manifest、业务主键/行 manifest、
  `data_version` 和 sidecar 状态不漂移；
- 对任何额外、缺失、弱化、未来、伪造或损坏 schema fail closed；
- 绝不调用 writable migration、canonical rebuild、补表或 marker repair。

当前仅创建少量旧表再让 v11 migrator 重建的测试不是 exact v0.3.1 证据，必须保留为一般
legacy migration 测试并另增真实 exact fixture 覆盖。

### 4.2 Privacy v1

新增 exact v1 只读 validator，逐对象匹配冻结 manifest，并执行 `quick_check`、
`foreign_key_check`、数据边界与受保护 payload 的 DPAPI 认证/解封验证。

Privacy v1 没有 workspace identity 或 lifecycle 表；缺少这些目标字段是合法源状态。预检不得
创建、补造或要求它们。无法认证的 protected payload 必须使升级 fail closed，不得丢弃、
替换或生成新身份掩盖错误。

### 4.3 源保持只读

从 source preflight 开始，直至 Privacy v6、binding/material 和 approved projection 全部
terminal，`user.sqlite` 必须保持 exact v10 且只读。测试必须注入写 SQL 并观察
`SQLITE_READONLY`，同时比较每个阶段前后的字节 hash 与语义 manifest。

## 5. 原态五槽加密回滚点

任何目标目录、workspace identity、Credential Manager key、Vault 或数据库写入前，必须先
建立一个 migration-only 原态回滚点。固定槽位为：

1. `user_database`：present / raw SQLite / schema 10；
2. `privacy_store`：present / raw SQLite / schema 1；
3. `vault_store`：authenticated absent；
4. `approved_workspace`：authenticated absent；
5. `work_products`：authenticated absent。

不得先创建后三个空组件再把它们描述为 v0.3.1 原态。普通 V3 backup wire contract 不改变；
migration recovery 可复用已经审计的 V3 AES-GCM/DPAPI 外层，但必须由独立、规范编码、
DPAPI-protected identity 明确五槽 `presence`、`encoding`、source profile、schema、长度、
component hash、logical manifest、bundle hash 和 migration id。普通 restore 必须拒绝该旧态包。

固定 source migration id 为：

```text
v0.3.1-to-v0.4.0-user-schema-v1
```

既有迁移 id 保持不变：

```text
project-privacy-case-binding-v1
case-material-unification-v1
approved-case-projection-v1
```

回滚点必须：

- 从同一固定 user/Privacy 只读快照生成；
- 使用每包新随机数据密钥并由 Windows DPAPI CurrentUser 包装；
- 对每槽使用域分离 AAD，absent 槽使用不同的规范 sentinel；
- 分开记录 creator app `0.4.0` 与推断的 source profile `v0.3.1-exact`；
- 不在 manifest 中保存案件正文、原文件名、路径、credential、token、ticket、receipt 或
  PrivacyCaseId；
- 以 no-replacement 语义先安装受保护 identity，再安装其精确 bundle；
- 从磁盘回读、解密、逐槽验证后才产生 backup receipt；
- 在提交前后再次证明两个源库未变、三个 absent 槽仍 absent；
- 在崩溃发生于 identity 和 bundle 两次安装之间时，只能恢复精确匹配的 staged bundle，
  不能覆盖或清理唯一有效回滚点。

## 6. 唯一升级状态机与顺序

升级 receipt 必须规范编码、DPAPI-protected、单调且可恢复，只保存版本、阶段、hash、计数、
时间和匿名错误码，不保存案件内容或 secret。允许状态严格为：

```text
source_preflight_verified
original_rollback_verified
target_components_prepared
case_migration_backups_verified
privacy_v5_verified
binding_materials_verified
projection_backup_verified
privacy_v6_verified
user_v11_verified
upgrade_complete
```

状态只能进入下一合法状态。组件仍在前一步时幂等重跑；组件与 receipt 不一致时 fail closed；
不得通过删除 receipt、修改 schema marker 或跳跃阶段继续。

### Step 0：恢复仲裁

1. 获取单实例锁和 migration operation gate。
2. 在任何 current manager 或 schema validator 前处理 pending full restore / migration rollback。
3. 已认证的中断升级只按 receipt 允许的下一步恢复。
4. 未识别 marker、sidecar 或部分状态停止启动。

### Step 1：只读证明源 profile

1. 固定并只读打开 exact user v10 和 Privacy v1。
2. 证明三个 target-only 组件以及对应 restore/staging 路径不存在。
3. 捕获文件、schema、业务行、项目主键和 protected payload manifest。
4. 完成容量、磁盘空间、路径、hardlink/reparse 和 DPAPI 预检。
5. 记录 `source_preflight_verified`；五个活动槽保持不变。

### Step 2：建立原态回滚点

1. 从同一源快照生成五槽 migration-only bundle。
2. 原子安装 identity 和 bundle并完成服务内回读恢复验证。
3. 再次证明源活动槽未变化。
4. 记录 `original_rollback_verified`。

没有该 receipt，后续任何目录、Credential、Vault 或数据库写入都是缺陷。

### Step 3：初始化目标专属组件

只有原态回滚点通过后，才允许创建目标 workspace identity、空 Vault schema 2、approved
workspace 和 encrypted work-products store。三组件必须为空、固定本地路径、普通单链接，
不得从项目字符串推导 Privacy identity。完成后记录 `target_components_prepared`。

### Step 4：建立 binding/material checkpoint

以 exact user v10 作为只读源，计算规范 source fingerprint。现有 Privacy v1 无 lifecycle，
因此原态回滚点是 v1→v5 和首次 binding/material 的先决 gate；如后续创建额外 checkpoint，
必须同样绑定原 v10 hash 和原态 identity。记录 `case_migration_backups_verified`。

### Step 5：Privacy v1→v5 与 binding/material

1. 在回滚 gate 后执行 Privacy v1→v5。
2. 初始化 binding、unified material、migration ledger、selection 和 lifecycle schema。
3. 先迁移 `ProjectId ↔ PrivacyCaseId` 绑定，再 backfill Privacy material/redaction 和
   CaseFile/attachment。
4. 无 Privacy/Vault 历史的项目才可安全随机创建新 PrivacyCaseId。
5. 可信唯一历史关联保留原 PrivacyCaseId；多候选、缺源或冲突写 blocked ledger。
6. 重跑只能 no-op 或继续未完成 ledger，不得产生第二绑定、第二 Vault 或第二 generation。
7. 每一批前后证明 user v10 字节与语义 manifest 未变。
8. 依次记录 `privacy_v5_verified` 与 `binding_materials_verified`。

### Step 6：Approved-only projection v5→v6

1. 在 Privacy v5 snapshot 上计算 projection source fingerprint。
2. 建立并回读验证 `approved-case-projection-v1` 五组件 checkpoint；此时 application backup
   允许 migration-source user v10，但普通 current backup/restore 仍只接受 v11。
3. 只对完整、可认证、仍 approved/current 的历史 generation 生成 canonical approved-only
   projection；loader 不得 fallback 到旧 full review blob。
4. 完成 projection hash、risk head、revocation、binding 和 security trigger 验证并提交
   Privacy schema 6。
5. 再次证明 user v10 未改变，依次记录 `projection_backup_verified` 和
   `privacy_v6_verified`。

### Step 7：最后迁移 user v10→v11

只有 Privacy 6、binding/material、projection 和五组件不变量全部通过后，才允许：

1. 再次验证原 v10 source fingerprint 和原态回滚 identity；
2. 在单一 SQLite immediate transaction 中执行 v10→v11 canonical migration；
3. 保留全部 ProjectId、项目、CaseFile、附件、会话、消息、artifact、run、proposal 和
   Provider 数据；
4. v10 历史会话明确迁入 ordinary assistant scope，不按 project/intent/artifact 猜测
   case-work scope；
5. 验证 exact v11 schema、关系、`quick_check` 和 FK；
6. 在 user operation audit、Privacy migration ledger 和 DPAPI completion receipt 中绑定同一
   lineage id、原 v10 hash、目标 v11 hash、原态 identity 和最终组件 manifest；
7. 记录 `user_v11_verified`。

禁止在 binding/material 或 projection 前把用户库迁到 v11。

### Step 8：最终维护与幂等启动

运行只属于目标 schema 的 recovery、retention 和 cleanup，验证所有 binding、Vault、
publication、work-product、revocation 和 assistant/export lineage。重启一次并证明全部迁移
为安全 no-op，最后记录 `upgrade_complete`，此后才开放普通 UI 与后台写操作。

## 7. Recovery-only `apply-and-exit`

旧态回滚包不能通过普通 restore 打开。用户显式选择后，migration recovery 必须验证 bundle、
DPAPI identity、source profile、completion lineage 和当前组件属于同一升级谱系。若 v0.4 后续
已有新数据，恢复前必须先建立 current v0.4 五组件安全备份，并明确恢复会回到旧态。

Recovery-only 进程必须：

1. 在任何 v0.4 manager、schema migration、maintenance、UI 或后台任务前运行；
2. 暂存并精确验证 user v10 与 Privacy v1；
3. 对三个 authenticated absent 槽，将当前 v0.4 组件先移动到 rollback 槽，不直接删除；
4. 在首次 swap 前再次验证 lineage 和全部 staged component；
5. 以可逆顺序提交五槽状态，每一步持久化进度；
6. 任一步失败时恢复完整 v0.4 五组件，不留下混合状态；
7. 成功后证明 user schema 10/marker、Privacy schema 1 和三个目标组件不存在；
8. 删除 incoming/rollback/pending residue，保留原态 bundle、identity、迁移报告和 current v0.4
   安全备份；
9. 返回 `AppliedDowngrade { target_app_version: "0.3.1" }`；
10. 当前 v0.4 进程立即以成功状态退出，后续 v0.4 初始化调用数必须为零。

恢复后 v0.3.1 必须实际能打开合成项目、会话和 Privacy 数据。用户以后显式再次启动 v0.4
时，应重新识别 exact source profile 并允许完整、幂等的再次升级；恢复审计 receipt 不得形成
永久阻止再次升级的 marker。

## 8. 测试冻结矩阵

### 8.1 Exact fixture 与 validator

- 从 peeled commit 真实代码生成并固定 user v10/Privacy v1 manifest 与 provenance；
- 正向接受 exact schema；
- 逐个修改或删除 table/index/trigger、marker、版本、FK、CHECK、额外对象均稳定拒绝；
- Privacy v1 没有 workspace/lifecycle 仍通过 exact validator；
- protected payload 错用户、损坏或无法解封时 fail closed；
- 校验前后源 DB/WAL hash、mtime、`data_version`、sidecar 和三个 absent 路径不变。

### 8.2 升级与只读

- 原态回滚点安装前零 workspace/Vault/Privacy/approved/work-product 写入；
- 五槽 identity 精确为 present/present/absent/absent/absent；
- user v10 在 target components、Privacy 1→5、binding/material、projection 5→6 全程只读；
- v10→v11 最后执行，保存所有合成业务数据和 ProjectId；
- completion lineage 只能在 v11 exact validation 后出现；
- 重启不产生第二绑定、Vault、material、generation 或 terminal ledger。

### 8.3 故障与篡改

至少在 identity/bundle 安装、target component 创建、Privacy 1→5、binding/material batch、
projection prepare/backfill/finalize、user transaction、completion receipt、五个 restore swap 与
cleanup 点前后注入失败。每一点必须安全 resume 或恢复前一完整状态。

任意 bundle、identity、sentinel、hash、filename、DPAPI user、workspace/lineage、hardlink、
reparse point 或 restore slot 篡改均必须在写入前 fail closed。

### 8.4 真实旧二进制验收

1. exact v0.3.1 fixture 升级至完整 v0.4 目标；
2. recovery-only 恢复原态并退出；
3. user 字节恢复为 bundle 内 v10、Privacy 恢复为 bundle 内 v1、三路径 absent；
4. 从 v0.3.1 tag 构建的真实代码打开并读取合成数据；
5. 再次显式启动 v0.4，升级成功且幂等；
6. 普通 V3 restore 仍拒绝 old schema/migration-only identity。

## 9. 提交分层

发布分支使用独立、可审计提交：

- R0：本计划及上位计划引用，docs-only；
- R1：exact user v10 / Privacy v1 validator、provenance 和负向测试；
- R2：原态五槽加密回滚点、receipt、启动恢复状态机和故障测试；
- R3：`apply-and-exit`、真实 v0.3.1 reopen/re-upgrade harness 和升级指南初稿；
- R4：发布脚本硬化、统一版本门、资产 allowlist 与服务端回读 verifier；
- R5：所有 manifest/lock/test fixture 同步到稳定 `0.4.0`；
- R6：CHANGELOG、Release Notes、中英文升级指南和当前用户文档；
- R7：最终候选完整验证；只修复本计划范围内的验证缺陷，不新增功能。

不得删除或弱化表征测试来使重构通过，不得用 TODO、空壳、假签名、占位模型或跳过测试冒充
完成。代码未部署时按 R6→R0 逆序回滚；升级已开始时不得 SQL down-migration 或单库恢复，
只能使用认证的完整五槽恢复路径。

点号规范名。映射、`.sig`、installer `.sha256` 和 `latest.json` URL/signature 必须同时验证。
App、paired MCP 与 installer 需要有效 Authenticode 和 RFC3161 timestamp；updater `.sig`
必须签署 exact 已签名 installer bytes。

### 11.2 MinerU component Release

使用独立 tag/Release `mineru-components-v0.4.0`，只包含：

- `mineru-component-catalog.json` 及 `.minisig`；
- `mineru-component-provenance.json` 及 `.minisig`；
- catalog 指定的唯一 `.laocrparts` descriptor；
- descriptor/catalog 精确列出的全部有序 `.partNNNN-of-NNNN`。

分片发布时不得同时上传未分片 `.laocrpkg`。历史 v3/v5 candidate、空/占位模型、合成包、
未批准 runtime/model/license/provenance 永久禁止进入 Release。

## 12. 发布脚本与服务端回读

Signed preflight 必须拒绝非 Windows、非稳定 0.4.0、非 main、dirty worktree、
`HEAD != origin/main`、远端未 fetch、版本漂移、缺失签名凭据、tag 漂移、final legal
resource/notices/CI closure 不完整。目录栈、cleanup 和错误码必须有行为测试，早期失败不得
消费 caller 的 location stack。

发布脚本必须使用 exact asset allowlist、禁止 wildcard/`--clobber`，只在远端已存在且指向
exact HEAD 的 annotated tag 上创建 draft。部分上传续跑时，服务端同名资产需先下载比 hash；
不同即失败，不覆盖。

上传后在全新临时目录下载全部资产，比较名称集合、数量、size 和逐文件 SHA-256，并重新执行
installer Authenticode/updater signature、portable manifest、三平台 MCP manifest/checksum 及
MinerU catalog/provenance/parts 全链验证。任何失败保持 draft，不删除、不发布。

## 13. CI、候选与 clean-machine 门禁

最终提交必须通过 UTF-8、全部 Python data/audit、MinerU worker/builder/qualification、Provider
mock/security、Rust fmt/clippy/workspace、实际 approved MCP stdio/HTTP、notices、前端
lint/test/build、Tauri packaging、release script/version/asset tests 和 `git diff --check`。

最终 `main` exact HEAD 必须同时通过主 CI 与 MCP Linux/Windows/macOS。跨平台 MCP archive
只从该 exact run 下载。真实计费 Provider、真实案件、真实 OCR 或外部 MCP 没有授权时不得
调用；相应 mock/contract 必须通过，真实调用如实标记 `not-run`。

Windows 10 与 Windows 11 clean-machine 至少验证：新安装、签名/publisher/timestamp、首次
启动、v0.3.1 升级、完整回滚、v0.3.1 reopen、再次升级、portable、updater、安装中断、卸载、
SmartScreen/AV/EDR。Final MinerU 还必须完成公开资产下载、签名链、短根安装、remeasure、
GPU/CUDA、firewall、process tree、synthetic canary、restart、drift/expiry/revoke。

## 14. GitHub Release 唯一顺序

1. 所有代码、版本、文档和测试合并到同步、干净的 `main`。
2. exact HEAD 的主 CI 与三平台 MCP CI 全绿。
3. 构建、签名并验证全部 App/MCP/MinerU assets。
4. 创建并推送不可移动的 annotated tags `mineru-components-v0.4.0` 与 `v0.4.0`，二者都指向
   最终 main commit；`v0.3.1` 保持原状。
5. 先创建两个 draft Release，上传 allowlist 并完成服务端回读。
6. 将同一 Release 发布为 prerelease；公开 URL 下完成 clean-machine、升级、回滚、portable、
   updater 和 MinerU qualification。
7. 先确认 MinerU component Release，随后把同一 `v0.4.0` Release 提升为 stable/latest，
   不创建第二 tag 或替换资产。
8. promotion 后立即重新下载 `/releases/latest/download/latest.json`，验证 bytes、version、URL、
   installer signature，并从 v0.3.1 完成最终 latest-endpoint 更新检查。
9. 最终端点失败时把同一 Release 降回 prerelease，停止正式宣告，不移动 tag/覆盖资产。

## 15. 外部门禁

仓库公开只解除 GitHub 下载可达性。以下缺失时可以继续完成源码与无凭据候选验证，但不得
创建或宣称 stable Release：

- 带私钥、有效期和可信时间戳能力的 Authenticode certificate；
- 与仓库内 updater 公钥匹配的 Tauri/Minisign private key 和密码；
- final MinerU v4 runtime/model revisions、完整 assets、Minisign 私钥、provenance/license/
  redistribution 人工批准；
- Windows 10/11 clean-machine 与目标 GPU/driver qualification 环境；
- exact final main commit 的全部 CI、签名、资产和服务端回读证据。

不得用占位证书、测试 key、历史 candidate、当前机器的普通 smoke test 或仓库 public 状态替代
上述门禁。

## 16. 完成判定

只有以下项目全部有证据，原定计划才算完成：

- exact v0.3.1 profile 自动升级与再次升级通过；
- 原态五槽回滚点在任何源写入前建立并验证；
- Privacy/binding/material/projection 期间 user v10 保持只读；
- Privacy 1→5→6 后最后事务迁移 user 10→11；
- recovery-only `apply-and-exit` 与真实 v0.3.1 reopen 通过；
- stable version gate、本地完整测试和 exact HEAD 跨平台 CI 全绿；
- Authenticode/updater/Minisign 凭据有效；
- 12 项 App/MCP 资产和完整 MinerU v4 签名资产完成；
- Windows 10/11 与 final GPU qualification 完成；
- 两个 Release 的 local/server SHA-256、签名和 allowlist 完全一致；
- 同一 Release 先 prerelease 验收后提升 stable，latest endpoint 最终通过；
- `main` 干净、同步，两个新 tag 指向最终 main，`v0.3.1` 未修改；
- 最终报告包含提交、测试、CI、资产、SHA、限制和同步状态。

任一项缺失时只能标记 `blocked`、`pending` 或 `not-run`，不能用“代码完成”“构建成功”或
“仓库已公开”替代正式发布完成。
